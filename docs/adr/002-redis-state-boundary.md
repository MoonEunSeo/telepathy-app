# ADR-002: Redis 휘발성 상태 경계

## 상태

수락됨 — 2026-08-22

## 맥락

현재 접속자 수와 일부 Socket.IO 상태가 Node 프로세스 메모리에 있어 다중 인스턴스에서 일관되지 않는다.
모바일 앱은 백그라운드 전환으로 연결이 자주 끊기므로 짧은 재접속 상태도 필요하다.

## 결정

Redis는 다음과 같은 재생성 가능한 상태만 담당한다.

- Socket.IO Redis Streams Adapter와 connection state recovery
- TTL 기반 presence와 접속자 집계
- 60초 재접속 상태
- 라운드·단어 단위 매칭 대기열
- 로그인·OTP·신고 rate limit
- 다중 인스턴스 스케줄 작업의 중복 방지

회원, 결제, 아이템 원장, 신고, 채팅 로그, 매칭 결과의 영속 원본은 PostgreSQL로 유지한다.

## 결과

- API 프로세스를 여러 개 실행해도 실시간 상태를 공유할 수 있다.
- Redis 장애 시 신규 매칭과 재접속이 일시 중단될 수 있다.
- Redis와 PostgreSQL에 같은 영속 상태를 중복 소유하지 않아야 한다.
- 모든 키에는 TTL 또는 명시적 길이 제한을 둔다.

## 대안

- 프로세스 메모리 유지: 비용은 없지만 수평 확장이 불가능하다.
- PostgreSQL만 사용: 영속성은 좋지만 presence와 고빈도 임시 상태에 불필요한 부하가 생긴다.
- Kafka: 현재 규모와 1:1 실시간 전달 모델에 맞지 않는다.

## 검증 기준

- API 인스턴스 2개에서 room broadcast와 접속자 수가 일치한다.
- 앱이 60초 이내 재연결할 때 세션을 복원한다.
- Redis 재시작 후 영속 데이터 손실이 없다.
- 키 수, 메모리, TTL, 명령량을 관측할 수 있다.
