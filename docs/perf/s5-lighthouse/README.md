# S5. 페이지 로드 종합 (Lighthouse)

> 조건: **production build (`npm start` → `localhost:5000`) / Lighthouse 12 CLI (headless Chrome) / 3회 중앙값**
> 다른 시나리오(S1·S4·S6)의 "Fast 4G"와 달리 **Lighthouse mobile 기본 스로틀**을 쓴다 —
> 시뮬레이션 Slow 4G(≈1.6 Mbps, RTT 150ms) + CPU 4x. 그래서 시간 지표가 더 크게 나온다.

## 목적

개별 시나리오(S1~S7)를 다 적용한 **뒤**, 사용자가 실제로 체감하는 페이지 로드를
표준 지표(FCP·LCP·TBT·CLS)로 종합 측정한다. "무엇을 더 해야 하는가"의 다음 타깃을 찾는 것이 목적.

## 측정 방법

```bash
npm run build                     # telepathy-front prod 빌드 (압축 S7 적용됨)
npm start                         # localhost:5000 (빌드된 프론트 + API)

# Lighthouse 3회 (performance 카테고리)
CHROME_PATH="…/chrome.exe" npx lighthouse@12 http://localhost:5000/ \
  --only-categories=performance --output=json --output-path=./lhN.json \
  --chrome-flags="--headless=new --no-sandbox --disable-gpu" --quiet
```

- 대상 URL: `/` (SPA 최초 진입 = 번들 다운로드 + 첫 페인트)
- Lighthouse 기본 mobile 프리셋(뷰포트 375×667 상당, Slow 4G + CPU 4x 시뮬레이션)

## 결과

| 회차 | 성능 점수 | FCP (ms) | LCP (ms) | TBT (ms) | CLS | Speed Index (ms) |
|---|---:|---:|---:|---:|---:|---:|
| 1 | 76 | 3,650 | 4,188 | 0 | 0 | 4,623 |
| 2 | 91 | 2,442 | 2,904 | 0 | 0.002 | 3,684 |
| 3 | 76 | 3,628 | 4,165 | 0 | 0 | 4,651 |
| **중앙값** | **76** | **3,628** | **4,165** | **0** | **0** | **4,623** |

> 회차 간 편차가 크다(76 vs 91). [README](../README.md) 가 경고한 "1회 측정은 노이즈가 지배"의 실제 사례다.
> 시뮬레이션 스로틀 + 로컬 환경의 스케줄링 편차 때문이며, 그래서 **중앙값(76)** 을 대표값으로 본다.

## 핵심 지표

| 지표 | 값 | 판정 |
|---|---|---|
| **TBT (총 블로킹 시간)** | **0 ms** | ✅ 최상 — 메인스레드 블로킹 없음 |
| **CLS (레이아웃 이동)** | **0** | ✅ 최상 — 로드 중 요소 밀림 없음 |
| FCP (첫 콘텐츠 페인트) | 3,628 ms | ⚠️ 느림 (스로틀 하) |
| LCP (최대 콘텐츠 페인트) | 4,165 ms | ⚠️ 느림 |
| 성능 점수 (중앙값) | 76 | 보통 |

## 분석

**① 인터랙션·안정성은 이미 최상이다 — TBT 0 / CLS 0.**
메인스레드를 오래 잡는 작업이 없고(TBT 0), 로드 중 레이아웃이 밀리지 않는다(CLS 0).
- TBT 0 은 [S2](../s2-form-rerender/README.md)(RHF 전환으로 불필요 리렌더 제거)와 결이 같다 —
  실행 시점에 JS 가 스레드를 오래 붙잡지 않는다.
- 즉 **"버벅임·밀림" 종류의 문제는 없다.**

**② 병목은 단일 JS 번들 크기다.**
FCP·LCP 가 ~3.6~4.2s 로 높은 이유는 **550 KB 단일 번들**(gzip/brotli ≈173 KB)을
Slow 4G 에서 받아 파싱·실행하기 때문이다. LCP 요소가 그려지려면 이 번들이 먼저 와야 한다.

주요 개선 기회(Lighthouse opportunities):

| 항목 | 예상 절감 |
|---|---|
| `unused-javascript` | ≈540 ms |
| `unused-css-rules` | ≈190 ms |

빌드도 같은 경고를 냈다: *"chunks larger than 500 kB … use dynamic import() to code-split."*

**③ 압축(S7)은 이미 반영돼 있다.**
이 측정은 압축이 적용된 prod 빌드 기준이다. [S7](../s7-compression/README.md) 이 전송량을 70% 줄였지만,
**다운로드는 줄어도 "단일 번들을 다 받아야 시작"하는 구조는 그대로**라 LCP 가 여전히 번들에 묶인다.
전송량과 로드 시작 시점은 다른 축이다.

## 개선 방향 — 다음 타깃은 코드 스플리팅

FCP/LCP 를 줄이는 지렛대는 **초기 JS 를 쪼개는 것**이다.

| 방식 | 내용 |
|---|---|
| **라우트 기반 분할** ⭐ | `React.lazy` + `Suspense` 로 페이지별 청크 → 최초엔 진입 페이지 것만 다운로드 |
| 무거운 의존성 지연 로드 | 결제(PortOne)·소켓 등 초기에 불필요한 모듈을 dynamic import |
| unused CSS 정리 | Tailwind 산출물 중 미사용 규칙 |

라우트 분할이 가장 효과가 크다 — 지금은 모든 페이지 코드가 한 번들에 들어 있어,
로그인 화면 하나 보려고 채팅·마이페이지·결제 코드까지 전부 받는다.

## 결론

- **런타임 품질(TBT·CLS)은 이미 최상** — 이번 perf 패스(S1·S2·S4·S6·S7)의 성과가 반영됐다.
- **남은 것은 "첫 로드 시간"이며, 그 원인은 단일 번들**이다. 압축(S7)으로 전송량은 줄였으나
  구조적 해법은 **코드 스플리팅**이다. 이는 별도 작업으로 남긴다.

### 미측정 / 한계

- **단일 URL(`/`)만 측정**했다. 라우트별 로드는 측정하지 않았다.
- **합성(lab) 측정**이다 — 실제 사용자 필드 데이터(CrUX/RUM)가 아니라 시뮬레이션 스로틀 기준.
- 회차 편차가 커(76~91) 중앙값을 썼다. 더 안정적인 값이 필요하면 5회 이상 권장.
- 원시 리포트(`lhN.json`)는 스크래치패드에 생성했고 저장소에는 커밋하지 않는다(위 명령으로 재현 가능).
