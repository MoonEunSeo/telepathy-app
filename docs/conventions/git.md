# Git 규약 — 브랜치·커밋

> 이 저장소는 **Linear**를 파이프라인으로 쓴다. 브랜치와 커밋에 이슈 식별자를 남기면
> Linear가 자동으로 이슈에 연결한다.

---

## 브랜치

```
codex/<타입>/<이슈식별자>-<주제>

codex/feat/tel-15-auth-module
codex/fix/tel-13-jwt-log
codex/docs/tel-11-db-guide
```

| 요소           | 규칙                                                                                                           |
| -------------- | -------------------------------------------------------------------------------------------------------------- |
| **타입**       | 커밋 메시지와 **같은 어휘**를 쓴다 — `feat` `fix` `refactor` `perf` `docs` `test` `build` `ci` `chore` `study` |
| **이슈식별자** | `tel-15` 처럼 소문자. **Linear 자동 연결의 핵심**                                                              |
| **주제**       | 영문 소문자 + 하이픈. 3~4단어 이내                                                                             |

- 전부 **소문자**, 공백 대신 `-`
- **한글을 쓰지 않는다** — 터미널·CI·일부 도구에서 깨진다
- 이슈가 없는 실험은 식별자를 생략한다 → `codex/study/tanstack-query`

### Linear 자동 연결

Linear 이슈 화면의 브랜치 아이콘을 누르면 이런 이름이 복사된다.

```
saver7942/tel-15-앱-계층-v2-이행-1차-모듈-구조zod-도입-및-신원-모듈
```

**그대로 쓰지 않아도 된다.** Linear는 브랜치 이름에 든 **이슈 식별자(`tel-15`)로 매칭**하므로,
위 규칙대로 짧게 지어도 연결이 유지된다. 한글이 섞이지 않아 다루기도 편하다.

연결되면 커밋·PR이 이슈에 붙고, PR을 열면 이슈 상태가 자동 전이된다.

### 계보 브랜치 (예외)

접두사 없이 쓰는 장기 브랜치다. 새로 만들지 않는다.

| 브랜치 | 용도                                                     |
| ------ | -------------------------------------------------------- |
| `main` | 초기 계보. 현재 활성 개발 대상이 아니다                  |
| `v2`   | 배포본 v2 계보                                           |
| `v3`   | **현재 작업 브랜치.** Render가 이 브랜치를 자동 배포한다 |

> ⚠️ **`v3`에 push하면 Render가 자동 배포된다** (트리거: commit).
> **코드가 한 줄이라도 섞였다면 push 시점 = 운영 반영 시점이다.**

### Build Filters — 문서 전용 push는 배포되지 않는다

Render 서비스 설정에 **Ignored Paths**가 걸려 있다.

```
docs/**
*.md
```

판정은 **커밋 단위가 아니라 push에 담긴 변경 파일 전체 기준**이다.

| push에 담긴 변경 | 배포      |
| ---------------- | --------- |
| 문서만           | ❌ 건너뜀 |
| 코드 포함        | ✅ 실행   |
| 문서 + 코드      | ✅ 실행   |

무시 대상 **밖의 파일이 하나라도 있으면 배포된다.** 문서를 묶어 보낸다고
코드 배포를 놓치는 일은 없다. 덕분에 문서 커밋을 따로 떼거나 배포를
피해 타이밍을 잡을 필요가 없다 — **평소처럼 push하면 된다.**

> 새 디렉터리를 Ignored Paths에 추가할 땐 주의한다. 나중에 그 경로에
> 빌드에 관여하는 파일이 들어가면 **배포가 조용히 걸리지 않는다.**
> 성격이 확정된 뒤에 추가한다.

#### ⚠️ Included Paths 칸에 넣으면 정반대가 된다

설정 화면에 칸이 둘 있다. **한 칸 위에 넣으면 의미가 뒤집힌다.**

| 칸                 | 의미                                                |
| ------------------ | --------------------------------------------------- |
| **Ignored** Paths  | 이것만 바뀌었으면 배포 **안 함** ← 우리가 원하는 것 |
| **Included** Paths | 이것이 바뀌었을 때**만** 배포                       |

`docs/**`를 Included에 넣으면 _"문서가 바뀔 때만 배포"_ 가 된다.
**서버 코드만 고쳐 push하면 배포가 안 나간다.** 에러도 알림도 없이
Events가 비어 있을 뿐이라, 원인을 찾기까지 오래 걸린다.

실제로 2026-07-28 이 상태로 잠시 설정돼 있었다. 그때 배포가 정상으로
보였던 건 **push에 문서가 섞여 있었던 우연** 때문이었다.

API로 확인하는 게 확실하다.

```
"buildFilter": { "ignoredPaths": ["docs/**", "*.md"], "paths": null }
```

`paths`가 `null`이어야 한다. 여기에 값이 있으면 뒤집힌 상태다.

## 커밋 메시지

[Conventional Commits](https://www.conventionalcommits.org) 형식에 **본문은 한국어**로 쓴다.

```
<타입>(<범위>): <제목>

<본문 — 왜 이렇게 했는지>

Co-Authored-By: ...
```

예시:

```
fix(supabase): publishable 키 사용처 제거 및 폴백 차단 (TEL-12 선행)

RLS 를 켜기 전에 반드시 선행돼야 하는 수정이다.
publishable 키는 anon 롤로 접속되므로, RLS 활성화 시 해당 경로만
권한을 잃어 조용히 실패한다.
```

### 타입

| 타입       | 쓰임                     |
| ---------- | ------------------------ |
| `feat`     | 기능 추가                |
| `fix`      | 버그 수정                |
| `refactor` | 동작 변화 없는 구조 개선 |
| `perf`     | 성능 개선                |
| `docs`     | 문서만 변경              |
| `test`     | 테스트 추가·변경         |
| `build`    | 빌드 시스템·의존성 변경  |
| `ci`       | CI 워크플로 변경         |
| `chore`    | 설정·잡무                |
| `study`    | 학습·실험 기록           |
| `revert`   | 이전 커밋 되돌림         |

허용 타입과 제목 길이는 `commitlint.config.mjs`가 커밋 시점에 검사한다.

### 범위

건드린 영역을 적는다. 실제로 쓰인 것들:

```
perf · auth · supabase · match · server · project · study
```

범위가 애매하면 생략한다 → `docs: ...`

### 제목

- **한국어**, 명사형으로 끝낸다 (`~ 전환`, `~ 추가`, `~ 차단`)
- 무엇이 바뀌는지 제목만 읽고 알 수 있어야 한다
- 관련 이슈가 있으면 뒤에 `(TEL-12)` 처럼 붙인다

### 본문

**무엇을 했는지가 아니라 왜 했는지**를 쓴다. 무엇을 했는지는 diff에 있다.

측정값·실측 근거가 있으면 함께 남긴다.

```
docs(perf): S6 After 측정 기록 — 소켓 push 로 폴링 59건/분 → ≈0
```

## PR

### 언제 여는가 — 계보 브랜치에 직접 push 하지 않는다

**`v3` 에 직접 push 하지 않는다.** 작업은 브랜치에서 하고 PR 로 합친다.

| 행위                    |                                        |
| ----------------------- | -------------------------------------- |
| 작업 브랜치에 커밋·push | **계속 한다** — 다른 PC 인계·백업 목적 |
| 완결 단위 도달          | **PR 을 연다**                         |
| `v3` 직접 push          | ❌                                     |

> 문서 전용 변경은 예외다. 리뷰 가치가 낮고 Build Filters 덕에 배포도 걸리지 않는다.

### 완결 단위로 쪼갠다

**큰 이슈를 한 PR 로 몰지 않는다.** 항목 단위로 나눈다.

TEL-15 는 7항목(로그인·회원가입·비밀번호·탈퇴·닉네임·게스트·응답규약)인데,
전부 끝내고 한 번에 올리면 diff 가 수백 줄이 되어 리뷰가 형식적이 된다.

쪼개는 기준은 **"그것만으로 검증이 끝나는가"** 다.
로그인 슬라이스는 타입체크·실동작 확인이 모두 끝나므로 단독 PR 이 된다.
회원가입은 4테이블 RPC 라 성격이 달라 같은 PR 에 묶을 이유가 없다.

### 본문

- 제목은 커밋 제목과 같은 형식
- 본문에 **Linear 이슈 식별자**를 넣는다 (`TEL-15`) → 자동 연결
- 본문에 **왜·검증 방법**을 적는다. 리뷰어가 무엇을 확인해야 하는지 알 수 있게
- **운영에 영향이 있는지를 맨 위에 적는다.** 리뷰어가 가장 먼저 알아야 할 것이고,
  미마운트·Feature Flag 처럼 영향이 없는 경우엔 그 근거와 롤백 방법을 함께 적는다
