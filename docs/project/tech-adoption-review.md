# 기술 도입 검토 및 기각 기록

> 검토일: **2026-07-27**
> 대상: Kafka · Spark · Elasticsearch · GraphQL
> 결론: **네 기술 모두 현 시점 도입하지 않는다.**

도입한 기술만 기록하면 "왜 안 썼나"에 답할 수 없다.
이 문서는 **검토했고, 근거를 갖고 기각했다**는 사실과 그 근거를 남긴다.

선례가 있다. [S3](../perf/s3-context-rerender/README.md)에서 Zustand를 측정 후 도입하지 않았고,
[성능 측정 원칙](../perf/README.md)에 이렇게 적어뒀다.

> "측정해보니 불필요해서 도입하지 않았다"도 유효한 결론이다.

---

## 판단 기준

기술을 넣을지 말지는 다음 순서로 판단한다.

| 순서 | 질문 |
|---|---|
| 1 | **이 기술이 푸는 문제가 지금 우리에게 있는가** |
| 2 | 있다면, **더 싼 수단으로 이미 풀렸거나 풀 수 있는가** |
| 3 | 그래도 필요하다면, **데이터·트래픽 규모가 손익분기점을 넘었는가** |
| 4 | 넘었다면, **운영 비용(금액·장애 지점·학습)을 감당할 수 있는가** |

1번에서 걸리면 나머지는 볼 필요가 없다. 아래 네 기술은 모두 1번 또는 2번에서 걸렸다.

## 1. Kafka — 기각

### 기각 사유

**① 채팅 메시지 전달에 Kafka는 오답이다.**
실시간 1:1 전달은 pub/sub 모델이 맞고, Kafka는 파티션 단위 순서 보장·재처리에 최적화된
분산 로그 시스템이다. 채팅 경로에 넣으면 지연만 늘어난다.

**② 현재 도메인에 Kafka가 필요한 지점이 없다.**
비동기 작업 큐가 필요한 지점(결제 후 아이템 지급 재시도 등)은 있으나,
그 규모에는 Redis Streams / BullMQ가 맞는다.

**③ 비용.** AWS MSK 최소 구성이 월 20만원을 넘는다. 개인·소규모 팀 프로젝트에 비현실적이다.

### 재검토 조건

- 매칭·신고 이벤트를 **다중 컨슈머가 각자 다른 속도로 소비**해야 할 때
- 이벤트 **재처리(replay)** 요구가 생겼을 때
- 그때도 self-host Kafka 또는 Redpanda(Kafka 프로토콜 호환, 단일 바이너리)를 먼저 검토한다

> 참고: [마이그레이션 계획안](https://linear.app/newtelepathy/document/텔레파시-기술스택-마이그레이션-2차-최종-계획안-c739c0490194) §4
> 「이번에 도입하지 않을 기술」에 Kafka가 명시돼 있다.

## 2. Spark — 기각

### 기각 사유

**① 규모가 4~5자릿수 어긋난다.**
Spark의 존재 이유는 "데이터가 한 대의 메모리에 안 들어갈 때 여러 대로 나눠 처리"다.
손익분기점은 통상 수억 행 / TB급이고, 그 아래에서는 **분산 오버헤드(직렬화·셔플·스케줄링)가
실제 처리 시간보다 크다.** 현재 전체 데이터는 24,679행이다.

**② 도메인이 맞지 않는다.**
Spark는 배치 분산처리 엔진이다. 이 서비스의 핵심은 15초 라운드 실시간 매칭이며,
무거운 집계 작업 자체가 존재하지 않는다.

**③ 대안이 훨씬 위쪽까지 커버한다.**

```
Postgres 집계 쿼리   →  수천만 행까지 충분
DuckDB               →  단일 노드로 수억 행 (임베디드, 인프라 0)
ClickHouse           →  수십억 행
Spark                →  그 위
```

현재 위치에서 Spark까지 세 단계를 건너뛴다.

### 재검토 조건

- Postgres 집계 쿼리가 **실측으로** 느려졌을 때 (가정이 아니라 측정)
- 그 시점에도 **DuckDB → ClickHouse 순서**로 먼저 검토한다

## 3. Elasticsearch — 기각 (단, 유일하게 명분이 생길 여지 있음)

### 기각 사유

**① 검색 대상이 761행이다.**
`chat_logs` 761행은 인덱스 없이 `ILIKE '%키워드%'`로 seq scan해도 1ms 미만이다.
수십만 행까지는 `pg_trgm` GIN 인덱스로 충분하다.

**② 새 장애 지점이 생긴다.**
Postgres → ES 동기화 파이프라인이 필요하고, 검색 결과와 원본이 어긋나는 문제는
운영에서 가장 성가신 종류에 속한다.

**③ 운영 비용.** AWS OpenSearch 최소 구성 월 5~10만원.
self-host해도 JVM 힙 때문에 2GB RAM은 상시 점유한다.

### 다만 — 기술적으로 틀린 선택은 아니다

Spark와 달리 ES에는 **언젠가 정당해질 시나리오가 하나 있다.**

> **한국어 전문검색.** Postgres 기본 full-text search에는 한국어 형태소 분석기가 없다.
> Supabase는 `mecab-ko`·`pgroonga` 같은 한국어 확장을 지원하지 않는다.
> "관리자가 신고 조사를 위해 채팅 로그를 키워드로 검색" 요구가 실제로 생기면 ES가 합리적 답이 된다.

즉 **"틀린 선택"이 아니라 "아직 이른 선택"**이다.

### 재검토 조건

- 관리자 신고 조사용 **채팅 로그 검색 요구가 실제로 발생**했을 때
- 그리고 `pg_trgm` 인덱스로 감당이 안 되는 규모(수십만 행 이상)에 도달했을 때

## 4. GraphQL — 기각

### 기각 사유

**① GraphQL이 푸는 문제가 이미 다른 방법으로 해결돼 있다.**

| GraphQL 도입 명분 | 현재 상태 |
|---|---|
| 오버페칭 / 요청 수 과다 | [S1](../perf/s1-duplicate-fetch/README.md) — TanStack Query 캐시로 15건 → 6건 (−60%) |
| 페이로드 크기 | [S7](../perf/s7-compression/README.md) — 압축으로 −70.4% |
| 타입 안전한 클라이언트↔서버 계약 | `shared/`가 이미 제공 (`api.ts`·`socketEvents.ts`·`domain.ts`) |

**② 측정된 유일한 남은 병목을 악화시킨다.**
[S5](../perf/s5-lighthouse/README.md) 결론은 "성능 점수 76, LCP 4,165ms, 원인은 단일 번들,
해법은 코드 스플리팅"이다. Apollo Client + graphql-js는 gzip 기준 **+40~50KB**(추정)로,
현재 gzip 152.5KB 대비 약 30% 증가다. **직접 측정해 병목으로 지목한 지표를 더 나쁘게 만든다.**

**③ 핵심 트래픽이 REST가 아니다.**
매칭·채팅·라운드 동기화·`onlineCount`·확성기가 전부 Socket.IO다.
[S6](../perf/s6-polling/README.md)에서 폴링 59건/분을 소켓 push로 ≈0까지 줄이기도 했다.
GraphQL을 넣어도 **핵심 트래픽에는 손을 못 댄다.** Subscriptions로 대체하려면
Socket.IO를 걷어내는 대규모 재작성이고, WebSocket 위에 프로토콜 레이어가 한 겹 더 얹혀
실시간 지연은 오히려 나빠질 가능성이 높다.

**④ 클라이언트가 사실상 1개다.**
GraphQL의 최대 강점은 이기종 클라이언트가 각자 다른 모양의 데이터를 요구할 때다.
계획안 §3.2는 "동일한 빌드 결과물을 Capacitor 기반 Android에 포함"으로 확정했다.
**웹과 앱이 같은 번들**이므로 요구 스키마는 하나뿐이고, 유연성은 순수 비용이 된다.

**⑤ 중첩 조회가 거의 없고, 오히려 N+1을 만든다.**
라우트 17개가 대부분 단일 리소스 CRUD다. 마이그레이션 후
`chat_sessions → members → messages` 구조가 생기지만 조인 쿼리 하나로 끝나는 깊이다.
반면 Supabase는 ORM이 아니라 REST 클라이언트라, 리졸버를 손으로 짜면 필드마다 쿼리가 나가
DataLoader를 직접 붙여야 한다.

**⑥ 계획안 §35 서버 구조와 정면 충돌한다.**
`Route → Controller → Validation(Zod) → Service → Repository`와
`ApiSuccess<T>` / `ApiError` 공통 응답이 이미 확정돼 있다.
GraphQL은 이 구조와 에러 모델을 통째로 무효화한다 (GraphQL은 실패해도 HTTP 200 + `errors` 배열).

### 부분적으로 맞는 지점

**관리자 페이지.** 신고 조사 시 `세션 → 참여자 → 메시지 → 신고사유 → 제재이력`으로
중첩이 깊어지고 운영자마다 필요한 조합이 다르다. 다만 화면 하나를 위해
전체 API 아키텍처를 바꾸는 것은 비용이 맞지 않는다.

### 알아둘 것 — Supabase에 이미 GraphQL이 있다

Supabase는 `pg_graphql`을 내장하고 있어 `/graphql/v1` 엔드포인트가 이미 살아 있다.
**서버를 다시 쓰지 않고도 GraphQL을 만져볼 수 있다.**

⚠️ 단, 현 상태에서 클라이언트를 여기에 직접 붙이면 안 된다.
**RLS가 전 테이블 비활성**이고([optimization-backlog](../perf/optimization-backlog.md) O8),
JWT 쿠키 기반 커스텀 인증(`role: member/guest`)을 통째로 우회하게 된다.
학습 목적의 격리된 사용은 가능하나 운영 경로로는 금지한다.

### 대안

| 원하는 것 | 더 나은 선택 |
|---|---|
| 타입 안전한 API 계약 | 이미 `shared/`로 보유. 더 원하면 **tRPC** — 단일 TS 저장소 + 클라이언트 1개인 이 스택에 더 맞고 런타임 번들이 거의 0 |
| 응답 크기 축소 | `select('*')`를 필요 컬럼만으로 축소 ([O5](../perf/optimization-backlog.md)) |

> 참고: 계획안 §4 「이번에 도입하지 않을 기술」에 GraphQL이 **이름으로 직접** 명시돼 있다.

## 요약

| 기술 | 판정 | 걸린 기준 | 재검토 조건 |
|---|---|---|---|
| **Kafka** | 기각 | 1 (문제 없음) | 다중 컨슈머 · 이벤트 재처리 요구 발생 시 |
| **Spark** | 기각 | 1·3 (문제 없음 + 규모 미달) | Postgres 집계가 실측으로 느려진 뒤, DuckDB부터 |
| **Elasticsearch** | 기각 | 3 (규모 미달) | 관리자 채팅 로그 검색 요구 + `pg_trgm` 한계 도달 시 |
| **GraphQL** | 기각 | 2 (이미 해결됨) | 이기종 클라이언트가 실제로 늘어났을 때 |

**공통 함정:** 네 건 모두 "기술을 먼저 정하고 명분을 찾는" 순서로 접근했다가 기각됐다.
순서를 뒤집어야 한다 — **문제를 측정으로 확인한 뒤 그 문제에 맞는 도구를 고른다.**

대용량 처리 경험이 목적이라면 순서는 이렇다.

```
부하테스트로 로그를 실제로 쌓는다
→ 집계·검색이 실제로 느려진다
→ 느려진 것을 측정한다
→ 그 시점에 도구를 검토한다
```

병목을 만들어낸 다음에 해결해야 근거가 생긴다.
