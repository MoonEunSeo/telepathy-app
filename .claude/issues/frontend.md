## 1. 인증 폼 React Hook Form 전환 (TEL-9)

`react-hook-form@7.82.0`. **zod 등 스키마 라이브러리는 도입하지 않는다** — 현재 검증 복잡도가 RHF 내장 `rules` 로 충분하고 번들을 늘릴 이유가 없다.

| 페이지 | 상태 |
|---|---|
| `ChangePassword.tsx` | 완료 |
| `LoginPage.tsx` | 작업 중 (미사용 import 정리) |
| `Register.tsx` | 작업 중 (타입 에러 잔존) |
| `FindPassword.tsx` | 미착수 — **멀티스텝이라 난이도 최상** |

목적은 코드량 감소가 아니라 **검증·에러표시·중복제출 결함의 구조적 제거**다.

### 기존 구조의 문제
- 검증 결과를 한 덩어리로 처리 → 길이 미달인지 불일치인지 구분 안 됨
- **중복 제출 무방비** — 4개 페이지 전부. 느린 네트워크에서 연타하면 요청이 N번
- **`<form>` 태그 자체가 없었다** → Enter 제출 불가, 비밀번호 관리자가 인식 못함. `LoginPage` 는 `<Button type="submit">` 이 있었지만 감싸는 `<form>` 이 없어 **아무 효과가 없었다**
- `ChangePassword`·`FindPassword` 는 `fetch` 에 `try/catch` 가 없어 네트워크 실패 시 **아무 피드백 없이 멈춘다**

### 선행 조건이었던 것
`AuthInput.tsx` 를 `InputHTMLAttributes` → `ComponentPropsWithRef<'input'>` 로 바꿨다.
**RHF 의 `register()` 반환값에 `ref` 가 포함되는데 기존 타입에는 `ref` 가 없어 spread 해도 실제 `<input>` 까지 도달하지 못했다. ref 가 연결되지 않으면 RHF 는 그 필드를 영구히 빈 값으로 인식한다.** React 19 에서는 `ref` 가 일반 prop 이라 `forwardRef` 없이 타입 변경만으로 해결된다.

`FieldError.tsx` 신규 — 입력창 하단 인라인 에러.

## 2. 재발 방지 체크리스트 (TEL-9 §8.3) — 2회 이상 발생한 것들

### ① 버튼 `type` (2회 발생)
`<form>` 안의 `<button>` 은 **기본이 `submit`** 이다.
- 제출 버튼 → `type="submit"`
- **그 외 전부** → `type="button"` (모달 확인, 중복검사, 돌아가기)

### ② `{...register()}` spread 순서
`register()` 는 `{ name, onChange, onBlur, ref }` 를 반환한다. JSX props 는 객체 병합이라 **같은 키는 뒤에 온 것이 이긴다.**
- spread 를 **마지막**에 둔다
- 값 변경 시 부수 동작이 필요하면 props 가 아니라 **규칙 객체의 `onChange` 옵션**을 쓴다
- `ref` 가 실제 `<input>` 까지 도달하는지 확인 — 아니면 그 필드는 영구 빈 값

### ③ 필드명 대조
placeholder 와 `register('필드명')` 이 일치하는지 **육안 확인**한다.

> 가장 위험했던 유형: 두 번째 입력창의 placeholder 는 "새 비밀번호" 인데 `register('confirmPassword')` 로 등록. **타입 에러가 안 나고 화면도 정상으로 보이는데** `validate` 의 `values.newPassword` 가 `undefined` 가 되어 일치 검증이 영구히 실패하고, 통과해도 서버에 `newPassword: undefined` 가 간다. `minLength` 검증도 함께 소실.

### ④ 편집 미저장 (3회 발생)
수정했다고 판단한 내용이 파일에 반영되지 않은 채 검사를 3회 반복했다. **검사 전에 저장 여부를 확인한다.**

## 3. 발견된 기존 결함

### 중복검사 결과가 낡은 채로 유지됨 — `Register`
아이디 중복검사 통과 후 아이디를 바꿔도 `isAvailable` 이 `true` 로 남는다.
```
"apple" → 중복검사 → 사용 가능 → "admin" 으로 수정 → 검사 없이 가입 통과
```
화면에도 "사용 가능합니다" 가 계속 떠서 **검증된 것으로 오인한다.**
→ **`register` 옵션 객체의 `onChange`** 로 값 변경 시 `isAvailable` 을 `null` 로 초기화. (props 로 `onChange` 를 주면 RHF 핸들러를 덮어써 폼이 안 돈다.)

### 비밀번호 강도 규칙이 페이지마다 다르다
| 페이지 | 규칙 |
|---|---|
| `Register` | 8자 이상 + 영문/숫자/특수문자 중 2종 |
| `ChangePassword` | 6자 이상 |
| `FindPassword`(재설정) | 6자 이상 |

**8자로 가입한 사용자가 비밀번호 변경으로 6자로 약화시킬 수 있다.** → 공용 모듈로 추출해 3개 페이지 통일. 반환 타입은 RHF `validate` 규약에 맞춰 `true | string`.

### ⚠️ 서버에 비밀번호 강도 검증이 없다 (별도 과제)
`register.routes.ts:19` 는 **값의 존재 여부만 확인**한다. 길이·조합 검증이 없다.
**즉 현재 비밀번호 강도 규칙은 클라이언트에만 존재하며, API 를 직접 호출하면 1글자 비밀번호로도 가입이 가능하다.**
클라이언트 검증은 UX 목적이지 보안 수단이 아니다. → `shared/` 에 규칙을 두고 클라/서버가 함께 쓰는 방안 검토. → [auth.md](auth.md)

## 4. 성능 — 적용한 7개 (TEL-10)

| # | 항목 | 결과 |
|---|---|---|
| 1 | 응답 압축 (gzip/brotli) | 첫 로딩 **−70.4%** (60만 → 18만 바이트) |
| 2 | 화면 전환 중복 요청 제거 (60초 캐시) | **15건 → 6건 (−60%)** |
| 3 | 입력 폼 리렌더 제거 | 글자당 **1회 → 0회** |
| 4 | 즐겨찾기·메모 연타 직렬화 | 경쟁 상태 차단 |
| 5 | 라운드 폴링 → **서버 푸시** | 분당 **59건 → 약 0건** |
| 6 | 전역 상태 관리 도입 여부 | **도입 안 함** |
| 7 | Lighthouse 종합 | 76 / 반응성·안정성 최상 |

### 남긴 판단
- **Zustand 등 전역 상태 라이브러리를 도입하지 않았다.** 가정했던 연쇄 재계산이 실측에서 **발생하지 않았고**, 원인은 다른 것(메인 화면 타이머, 항목 5)이었다. 서버 데이터를 캐시가 가져가면서 공유할 전역 상태 자체가 줄었다. **"측정해보니 불필요해서 도입하지 않았다"도 유효한 결론.**
- 항목 4 는 **측정 당시 재현되지 않았다(0/6회).** 재현되지 않던 위험을 구조적으로 차단한 것이며, **요청 수를 줄이지는 않는다**(직렬화이지 제거가 아님).
- 항목 1 은 첫 로딩 얘기다. **개별 API 응답은 0.3~0.4KB 라 압축 대상이 아니다** — 항목 2 와는 다른 축이고 겹치지 않는다.

### 캐시 무효화를 건 지점 (정확성)
- 확성기: 구매·발사 직후 (구매했는데 "없음" 오판 방지)
- 로그인 상태: 로그인·로그아웃·탈퇴 직후 (로그인 직후 보호 페이지에서 튕기는 문제 방지)
- 인증 상태 확인이 **페이지 이동마다** 재요청되고 있었다(4회 중 3회 불필요) → 조회 1회, 접근 권한 판정만 이동 시 수행하도록 분리

### ⚠️ 라운드 푸시 전환의 회귀 지점
기존 폴링은 로그인이 필요 없었으나 **서버 푸시는 실시간 연결에 인증이 필요하다. 게스트가 연결되지 못하면 라운드 전환을 통째로 잃는다.** 게스트 세션 정상 연결을 확인해야 한다. → [matching.md](matching.md)

### 남은 과제
1. **코드 스플리팅** — 가장 우선. 지금은 모든 페이지 코드가 한 덩어리라 로그인 화면 하나를 보려 해도 채팅·마이페이지·결제 코드까지 전부 받는다. Lighthouse 가 가리킨 다음 타깃.
2. 연타 시 요청 수 감소 (처리 중 버튼 비활성화)
3. 실시간 연결 최초 진입 조회 통합
