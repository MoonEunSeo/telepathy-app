> 리니어 요약본. **다르면 리니어가 맞다.** 갱신 2026-08-05

## 1. 문제 두 개

### (1) 확성기 잔액이 카운터다
레거시는 `users` 의 숫자 컬럼을 증감한다. **왜 늘었는지·줄었는지 추적할 수 없고, 동시 요청에서 유실될 수 있다.**
V2 는 `user_item_ledger` **원장**으로 바꾼다 — **잔액은 원장의 합이다.**

### (2) 확성기 구매가 지금 동작하지 않는다
PortOne 제거(PR #14) 후 PG 결제 경로가 사라졌다. 웹훅 수신부(`webhook.routes.ts`)와 계좌이체 생성(`sp_payments.routes.ts`)은 남아 있으나 **단어세트 전용이고 재화를 지급하지 않는다.** 지급 로직이 새로 필요하다.

> **PG 결제는 §27.1 대로 범위 밖**(실적 0건 — 운영 `payments` 테이블이 실제로 0행이었다). **확성기는 계좌이체 웹훅으로 복구한다** (2026-08-04 확정).
> 운영의 결제 엔드포인트가 **500 을 반환하는 것은 의도된 상태**다 (커밋 `b38af8c`). 이 항목에서 정상화한다.

## 4. 착수 전 확인

- **계좌이체는 2단계다.** 주문 생성 시점과 입금 확인 시점이 다르다. **지급은 웹훅 수신 후**여야 하고, **결제 기록과 지급이 한 트랜잭션**이어야 한다. (PR #9 에서 같은 문제를 이미 한 번 고쳤다.)
- **웹훅은 재전송된다.** 같은 입금이 두 번 오면 재화가 두 번 지급된다. `payment_events` 로 멱등성을 보장한다(`event_key` UNIQUE).
- **입금 웹훅 129건 중 주문에 연결된 기록이 0건**이다(TEL-11). 어느 입금이 어느 주문을 결제완료시켰는지 **DB 로 추적할 수 없는 상태.** V2 는 구조를 마련했으나 **레거시 데이터에는 연결 정보 자체가 없어 복원 불가**다.

## 5. 리플레이·TOCTOU — 이미 한 번 데인 자리 (TEL-7 §3.5)

레거시는 **"지급 → 기록"** 순서라 UNIQUE 제약이 있어도 **이미 지급된 뒤 insert 가 실패**했고, 그 오류를 `console.error` 만 하고 `success` 를 반환했다.

> **조회 후 거절(select → insert)은 확인과 기록 사이의 시간차(TOCTOU) 때문에 동시 요청을 막지 못한다.** DB 제약을 통한 원자적 판정이 필요하다.

→ `payments` insert 를 지급보다 **먼저** 실행하고, 중복(SQLSTATE `23505`)이면 **409 반환 후 종료**해 지급에 도달하지 않게 했다. 검증: 연타·동시요청 5건 중 1건만 지급, 나머지 409.

**실증된 피해** (TEL-7, 레거시): 남의 유료 확성기 차감 + 그 사람 이름으로 전체 방송 / 클라가 count 를 정해 1,000원 결제로 확성기 9,999개 / 동일 `imp_uid` 반복 제출로 무제한 충전 / 남의 환불계좌를 자기 계좌로 변경 / **무인증 `/api/deposit` 웹훅으로 입금 없이 결제 완료 처리**.

**원칙 — 돈이 걸린 값(가격·수량)은 서버가 소유한다.** 클라는 `item`(SKU) 만 전달하고 가격·수량은 서버 `SKU_TABLE` 이 결정한다.

## 6. RLS 를 켜기 전 선행 수정 (TEL-12) — 중복 기재

`server/src/routes/payments.routes.ts` **만** `SUPABASE_SERVICE_ROLE_KEY` 가 아니라 `SUPABASE_KEY`(publishable)를 썼다. **이 상태로 RLS 를 켜면 확성기 구매가 깨진다.**

→ 커밋 `7da7362` 로 제거 완료. 서버 코드에 `SUPABASE_KEY` 참조 0건. 운영 RLS 적용 시 **확성기 구매 정상 동작을 먼저 확인**해야 원인 구분이 가능하다.

## 7. 이관 데이터의 한계

- cutover 는 **`order_items` 를 의도적으로 비운다** — 레거시에 상품 마스터가 없어 **무엇을 샀는지 복원할 수 없다.** 신규 주문부터 채운다.
- 확성기 잔액은 이관 시 `ADMIN_GRANT`(잔액+사용분) + `USE` 행으로 재구성했다. **과거 지급 사유는 실제 사유가 아니다.**
- **환불 계좌를 저장할 곳이 없었다** → `payments` 에 `refund_bank`·`refund_account` 컬럼 2개 추가(TEL-11). `legacy_sp_payment_id` 매핑으로 **24행 복구 확인.** 계좌번호는 개인정보이므로 **암호화 여부 판단 미결**(평문/앱 암호화/별도 보관).
- **결제한 34명 중 7명이 `users` 에 없다** — 탈퇴 시 물리 삭제 때문. **돈을 낸 사람의 계정이 사라져 환불·정산 추적이 불가능하다.** 되돌릴 수 없고, 이 전환은 더 늘지 않게 막는 것이다. → [auth.md](auth.md)
